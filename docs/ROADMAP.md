# Roadmap

What exists, what is being built, and what is planned. Anything that touches a real RadioDJ, ElevenLabs, OpenRouter or Netlify Blobs is **not verified live** until it says so (the lists are in [HUB.md](HUB.md#needs-live-verification-on-a-real-radiodj-do-not-claim-any-of-these-works-until-it-has-been)).

## Built (tested against fakes)

- Two clocks (`broadcastTz`, `machineTz`) everywhere, with warnings. Scoped service keys (`SERVICE_KEYS`).
- RadioDJ agent: status, schedule, insert two ahead and preempt the planned clip, hash-named ingest, kill switch, live-show refusal, audit log, pull loop for a PC behind NAT.
- Hub: just-in-time drops (shadow mode default, approval queue, caps, breaker, fail open), pull endpoints, audit log. See [HUB.md](HUB.md) sections 10 and 11.
- Dynamic tab: status, clocks, review and approve, slots (with saved scripts), spend, audit.
- Scripts and the Studio ([SCRIPTS.md](SCRIPTS.md)): casting up to four speakers, AI drafting from persona briefs, saved scripts, conversations in schedules and dynamic slots, save and schedule from the Studio. Weather report format and placeholders in generation and schedules.
- Grouped menu, mobile layout.
- Freshness classification (hub module, tested against fakes): rules tier a script as static, daypart, refreshable or live from its text; an optional Jev second layer asks seven atomic questions and can only demote. Not wired into the UI or the hub flow yet. [FRESHNESS.md](FRESHNESS.md).
- OpenRouter's own `elevenlabs/` speech models are spoken through OpenRouter, and a direct ElevenLabs choice falls back to them while no ElevenLabs key is set.

## Next

1. **Song-neutral evergreens.** A planned clip at a dynamic slot may not name a song, an artist or "the next song" (it may be a station ID, time check, generic break, promo or weather). A `songNeutral` flag on slots and an audit of the baked drops. Needed before requests, because a requested song changes what plays next.
2. **Song requests.** A channel-agnostic request (`source`: `ui` now; web form, email, chat later): song, requester first name, optional dedication, state (pending, matched, approved, queued, played, rejected, failed). A Requests panel in the Dynamic tab takes a request by hand, matches it to the library, and a person approves it. The song is inserted at least two ahead (same insert mechanism, with a library file) and the neighbouring host break is written with exactly the names that really play (`constraints.names`), thanking the requester by first name. Rate limits, a blocklist and the language checks apply to every requester-supplied word; contact details are kept apart from what the writer sees. **Decided: requests are shared with the audience**: a public request list (what was asked, by first name, and its state: queued, coming up, played, after the show) so listeners see each other's requests, and requesters can see where theirs is. Only the song, first name and state are public; contact details and dedications under review never are. Automatic bringing-in of approved requests is allowed but always yields to relay shows (see below). Needs from Sylvia: a way to find a song in RadioDJ's library by artist and title, and the insert script.
3. **Relay shows.** A `Show` (name, host, recurring time in `broadcastTz`, relay source such as an Icecast mount or URL, grace window) drives four things from one schedule: its **promos** (a site schedule that stops when the show starts and expires with it), a dynamic **intro and outro** slot, an **agent watch** that switches to the relay only once the source has been up for a few seconds and back when it drops or the show ends plus the grace period, and **Dynamic/Control** status with manual "go to relay now" and "return to automation". A `relay` agent mode, like `live-show`, suppresses dynamic drops and refuses insertions.
   **Decided: a relay show preempts every other kind of automated programming**, including requests that would otherwise be brought in automatically: while a relay show is live (and during its promo lead-in, if the show says so) the hub inserts nothing, requests wait in their queue (they are not dropped, and are shown to their requesters as "after the show"), and the planned playlist resumes when the relay ends. Precedence, highest first: kill switch, relay show, live show, requests, dynamic drops, planned playlist. How the stream actually switches (RadioDJ, Liquidsoap or Icecast fallback mounts) is the unverified part: it will be a hook like insert. Open questions: what the relay source is, how DJs authenticate, what happens if the DJ never shows (wait the grace window, then skip and replay the promo?).
4. **Google Calendar.** Publish the schedule for the audience: shows, relay shows and promoted events become calendar events, updated automatically when a show is created, moved or cancelled. **Decided horizon:** one-off events (a special, a promoted event, a relay show that is not weekly) are published **4 weeks ahead**; shows and programs with a recurring schedule are published as **recurring events** (an iCalendar `RRULE` in the station's `broadcastTz`, so daylight saving is handled by the calendar) with **no end date**, so they run into the future for as long as they exist, until the show is removed (the series is deleted) or updated (the series is changed, with exceptions for single cancelled or moved dates). Plan: a station calendar owned by a service account (calendar id on the station); events carry the show name, host, an explicit time zone, a listen link and a description; each series and each one-off is keyed by a stable id derived from the show, so an update edits the same event and a removal deletes it; an `.ics` feed (`/api/calendar/<station>.ics`) is the account-free way to subscribe (it carries the same recurring rules), and a public calendar embed goes on the website. One direction only (the site writes, nothing reads back). Needs: a Google Cloud service account with the calendar shared to it, a nightly batched sync that respects API quota, and the Show model from item 3 as the single source. *Planned, not built.*
5. **Intake adapters for requests and messages:** a web form on the site, email, and chat apps, each a small source with its own scoped key posting to the same request endpoint.
6. **Freshness tiers in use.** Classify scripts on save, store `freshness`, `reasons`, `needsReview`; reuse `static` clips, regenerate `refreshable` only when values change, queue `live` slots with a fallback; badges, a review queue and an override in the UI. Then switch on the Jev second layer after measuring it. Spec and rollout: [FRESHNESS.md](FRESHNESS.md).
7. **Five-minute working lead for live slots,** measured to the swap deadline (the start of the item before the slot), so `leadSeconds` = 300 + the preceding item's duration. [FRESHNESS.md](FRESHNESS.md).
8. **Show promos on a cadence** (next show and start time from the plan file, voices rotated evenly) and **simulated call-ins** (host, caller, host; caller voice bank; phone filter on the caller turn only). Both come from the Green Light scripts; details and acceptance tests in [GREEN-LIGHT-PARITY.md](GREEN-LIGHT-PARITY.md) sections 1 and 2. Open question for the station owner: whether callers must be marked as simulated.
9. **The rest of the Green Light feature parity list** (recap back-announce, placement validator, spoken-name cleanup, DJ shifts, taste-based rotation, same-room voice profile, ops endpoints): [GREEN-LIGHT-PARITY.md](GREEN-LIGHT-PARITY.md).
10. **Lore graph for host personas** (planned, not built): station lore as nodes and edges, imported from CSV or TXT, scoped per persona and approved before use, with a CLI explorer and retrieval into script prompts. See [tickets/LORE-GRAPH.md](tickets/LORE-GRAPH.md).

## Platform (not needed yet, but several of the items above depend on it)

- **A real backend and database.** Today the site keeps everything in Netlify Blobs (one file per record, no queries) and the hub keeps one JSON file. Both are fine for one station and a few hundred records. The things planned here need more: shows with recurring rules and exceptions, a public request list with live state, per-requester history and rate limits, audit trails across stations, calendar sync state, and chat messages. When the first of those is built, move storage behind the existing store modules (`lib/*-store.ts`, `chips-voice/hub/store.js`, which are the only files that touch storage) to a hosted SQL database such as Postgres, with migrations, backups and retention rules for personal data (requester names and contacts). Needs a decision on hosting (a managed database next to the hub, or the site's host) and on whether the hub and the site share it.
- **A chat platform** for listeners and DJs (live chat during shows, request conversations, announcements), probably a hosted service or an open-source server that the site embeds, with moderation tools and the same language and blocklist checks as everything else on air. It needs the database above for accounts, history and moderation records, and it is the natural home for the intake adapters in item 5. Not designed yet.
- **Run the hub layer on Netlify** instead of a separate server: pull endpoints as functions, the tick as a one-minute scheduled function that hands each due slot to a background function (scheduled functions stop at 30 s, background ones at 15 min), per-record Blobs keys instead of one JSON file, a lock per slot, audio in Blobs. The RadioDJ agent stays on the station PC. Main risk: concurrent writers on the store. Not started.

## Later

- Emergency alerts: official National Weather Service text verbatim, area-filtered, human approval, kill switch, off by default. Today only a refusing hook exists.
- A real database for the hub (it is one JSON file now, fine for one station).
- Conversation drops that are generated per station group with different casts.

Everything that is neither built nor listed here (legal station IDs, effects in scripts, monitoring, licensing, public-page abuse protection, DJ accounts, and more) is in [HANDOFF.md](HANDOFF.md).
